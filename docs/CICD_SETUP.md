# CI/CD setup guide (Terraform + GitHub Actions on AWS)

How the pipeline works: a push to `main` runs the tests, then builds two Docker images
(tagged with the short commit SHA), pushes them to Amazon ECR, runs `terraform apply`
to roll the new version out on ECS Fargate behind a load balancer, and checks that
`/api/health` reports the new build ID.

## 0. Prerequisites (one team member does the AWS part)

- An AWS account and the AWS CLI configured (`aws sts get-caller-identity` works)
- Terraform **1.10 or newer**, Docker, Git
- A GitHub repository for the team (everyone is a collaborator)

## 1. Push this project to GitHub

```bash
git init -b main
git add .
git commit -m "Initial commit"
git remote add origin https://github.com/OWNER/REPO.git
git push -u origin main
```

(The first push will start the Deploy workflow and fail because AWS is not set up yet. That is
expected. Do steps 2 and 3, then re-run it.)

## 2. One-time bootstrap (state bucket + GitHub-to-AWS trust)

```bash
cd infra/bootstrap
terraform init
terraform apply -var="github_repo=OWNER/REPO"
```

If the account already has a GitHub OIDC provider, add `-var="create_oidc_provider=false"`.
Note the two outputs: `state_bucket_name` and `github_actions_role_arn`.

## 3. Configure GitHub (Settings, then Secrets and variables, then Actions)

| Type | Name | Value |
|---|---|---|
| Variable | `AWS_REGION` | `us-east-1` |
| Variable | `AWS_ROLE_ARN` | output `github_actions_role_arn` |
| Variable | `TF_STATE_BUCKET` | output `state_bucket_name` |
| Secret | `ADMIN_PASSWORD` | a long passphrase (12+ characters) for the admin page |

Then:
- **Settings, Environments, New environment: `production`.** Add required reviewers (teammates) if your plan allows. This is your deployment approval gate.
- **Settings, Branches, add a rule for `main`:** require a pull request and require the CI checks to pass. This is the "approved branch".

## 4. Format, initialise, validate and plan locally (Task 3 evidence)

```bash
cd infra
terraform fmt -recursive          # fixes formatting; commit the result
terraform init -backend-config="bucket=<STATE_BUCKET>" -backend-config="region=us-east-1"
terraform validate
export TF_VAR_admin_password='a-long-passphrase'
terraform plan
```

Commit the generated `infra/.terraform.lock.hcl`. Take screenshots of each command for your report.
Run `terraform fmt -recursive` in `infra/` once before your first pull request, otherwise the CI
formatting check will fail.

## 5. First deployment

Open a pull request, let CI pass, get it approved and merge. Go to **Actions**, open the
Deploy run and approve the `production` environment if asked. When it finishes, the run
summary shows the application URL. (The first run takes about 8 to 12 minutes because the
load balancer and service are being created.)

## 6. The demo (Task 4)

1. Open the live URL and show the **Build** ID in the footer.
2. Edit a visible text, for example the tagline in `frontend/src/pages/Home.jsx`, on a branch.
3. Open a pull request, show CI running (tests, `terraform fmt`, `terraform validate`, Docker build).
4. Merge to `main`. Show the Deploy workflow running and the approval step.
5. Refresh the site: the new text and a **new Build ID** appear. Later runs take about 3 to 5 minutes.

## 7. Clean up (avoid charges)

After the demo and marking: **Actions, Destroy infrastructure, Run workflow, type `destroy`.**
Then, optionally, `terraform destroy` in `infra/bootstrap` (empty the state bucket first).

## Good to know

- The SQLite database lives inside the task, so content edited in the admin page resets on each deployment. The app reseeds the starter content automatically.
- The load balancer gives the site a stable address; without it the public IP would change on every deployment.
- Secrets: the admin password comes from a GitHub secret and is stored in AWS Secrets Manager; the JWT key is generated by Terraform. Neither is in the repository or the Docker images. Terraform state can contain them, which is why the state bucket is private, encrypted and versioned.
- The GitHub role has `AdministratorAccess` to keep the demo simple, but only this repository's `main` branch or `production` environment can use it.
- Rough running cost: about 1.5 US cents per hour for the load balancer plus about 2 cents per hour for the Fargate task.
